# Proposed Data Model

This is a logical model, not a final physical schema. Existing repository/database schema must be inspected first. Reuse compatible existing entities and avoid destructive rewrites. Exact column types, indexes and migrations are implementation details that must be documented and tested.

## 1. Academic structure

### `academic_terms`
- `id`
- academic year / term label
- semester number (1–8)
- term start/end dates
- odd/even cycle metadata if needed
- status (planned/active/closed)
- configured non-teaching dates/relationship to calendar

Terms and dates are admin-configured; the August–December and January–May pattern is contextual guidance, not hardcoded term boundaries.

### `sections`
- `id`, code/name, semester/term relationship, active status

### `batches`
- `id`, section relationship, code/name, active status

### `students`
- `id`, university student identifier, verified account relationship, active status

### `student_group_memberships`
- student, group/section/batch, effective start date, effective end date (nullable), audit reference
- supports effective-dated transfers; do not rewrite historical membership periods

### `elective_groups` and `elective_assignments`
- elective group metadata (course/term/context)
- assignment: student, elective group, effective period/status, assigned by admin, source/import reference
- assignments come from authorized admin entry or validated import, not student self-service
- transfer incompatibility flags should be explicit and resolvable; don't auto-delete assignments

## 2. Teaching resources

### `teachers`
- `id`, university identifier, account relationship, active status

### `teacher_availability`
- teacher, recurrence/weekday or date scope, start/end slot/time, availability state, created/updated by
- regular availability is admin-managed

### `teacher_unavailability_requests`
- teacher, date/time range, optional reason, request status, submitted timestamp, reviewed by, reviewed timestamp, decision/reason
- only an approved/confirmed request affects availability

### `rooms`
- `id`, room number, building, floor, capacity, room type (`LT` or `P`), active status

## 3. Course and timetable data

### `courses`
- `id`, course code/name, term/course catalog reference, L/T/P weekly contact-hour values, configured session pattern or exception reference, required room type and optional expected group size rule
- odd practical-hour handling must not be guessed; unresolved values should fail validation with an actionable message

### `course_offerings`
- course, term, target section/batch/elective group(s), assigned teacher(s), required weekly sessions as expanded from approved session rules
- supports a course teaching lecture to a whole section and lab/tutorial to a sub-batch

### `timetable_configuration`
- version, operating days, named slots/periods, slot start/end, break/non-teaching flags, default session rules, optimization preferences and effective dates
- values are configurable, not literals scattered through code

### `generation_runs`
- id, requested by, status (`queued/running/succeeded/infeasible/failed/cancelled` as applicable), start/end timestamps, input revision/hash, generator version, diagnostics, output reference
- status updates must be durable and not imply success until output is validated and saved as a draft

### `generation_input_packages`
- id/version, generated by/admin, data revision/hash, schema version, created timestamp, manifest and package reference
- package contains only required dummy or authorized scheduling inputs; no secrets

### `timetable_versions`
- id, term/cycle scope, version number, status (`draft/published/superseded/archived` as needed), created by, created timestamp, source generation/import, published timestamp, prior-version relationship
- generated and imported output is draft until explicit publish

### `scheduled_classes` / `class_occurrences`
- version or recurring-pattern link, course offering, date (for dated occurrence), start slot, duration in slots, activity type L/T/P, teacher, room, target group, status
- support one-slot L/T and two-consecutive-slot P under configured rules
- keep recurring pattern separate from occurrence exceptions and extra classes

### `class_occurrence_events`
- occurrence reference, event type (cancelled/rescheduled/room changed/teacher changed/replacement etc.), prior/new values or immutable payload, reason, actor, timestamp
- enough history to render cancelled vs replacement classes without deleting the original event

### `extra_classes`
- one-off date, course/activity, teacher/booking teacher, target groups, room, start slot/duration, status, created by, timestamps
- never writes into recurring timetable pattern
- enforce owner/admin cancellation/reschedule authorization

## 4. Identity and audit

### `profiles` / account mapping
- Auth provider user ID, university email, account status, university identity link
- role assignment only by authorized admin; first release has student, teacher, admin roles

### `audit_events`
- actor, action, entity type/id, timestamp, request/correlation ID, result, change summary/version references
- avoid secrets and sensitive data in payloads; do not store plaintext passwords or credentials

### `notification_outbox` / `notifications`
- affected user, event type, safe content/reference, created time, delivery status/retries, idempotency key
- persist logical event in same transaction as schedule mutation when possible; actual external delivery can occur after commit

## 5. Relations and invariants

- Group/section membership and elective assignment must be resolvable to actual students for conflict validation.
- A multi-slot occurrence occupies every slot in its interval and reserves the same room across the entire interval.
- A published version is immutable as a published snapshot; changes go to a new draft.
- A failed generation/import never overwrites the current published version or partially inserts draft rows.
- Audit history is append-only or otherwise protected from ordinary user mutation.
- Version/hash metadata must allow stale-input detection; an override is recorded and followed by current-data validation.
- Use database constraints/transactions/locking as needed for race safety; don't rely only on application-side `check then insert`.

## 6. Schema implementation instructions

Before migrations: inspect the current database, document existing tables, identify conflict/uniqueness mechanisms, and take a non-destructive approach. Do not drop tables, truncate data or create a reset routine. Provide migration and rollback notes. Do not use production data during prototype development.
